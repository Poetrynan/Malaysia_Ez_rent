# RAG 知识库优化路线图

> 创建时间：2026-06-05
> 当前状态：知识库已上线（132 小区 / 42 大学 / bge-m3 embedding）

---

## 1. 前端展示优化 — 知识库结果渲染

**当前问题：** Agent 调用 `search_knowledge_base` 返回了丰富的小区数据（价格、评分、设施等），但前端没有对应的 UI 组件来展示。目前只有 `search_internal_db` 的结果会触发 `MapAndCard` 组件渲染地图和卡片，知识库的结果只会以纯文字形式输出。

**为什么要优化：**
- 用户问"Sunway 附近有什么小区"，Agent 文字回复了一堆信息但没有地图标注，体验差
- 知识库有经纬度数据，完全可以展示在地图上
- 有评分、价格范围等结构化数据，适合用卡片展示而不是纯文字

**具体要做：**
- 在前端 `MapAndCard` 组件中支持 `is_knowledge_base` 模式
- 知识库结果展示：小区名 + 价格范围 + 评分 + 到大学距离
- 地图上标注多个小区位置（而非只标一个）

---

## 2. 外部搜索结果格式化

**当前问题：** Tavily 联网搜索已经放开（可以搜 iProperty、PropertyGuru 等），但搜回来的是原始网页片段，Agent 直接拼接文字回复，没有结构化处理。

**为什么要优化：**
- 用户问"有没有具体的房源"，Agent 搜到的可能是杂乱的网页摘要，信息密度低
- 不同平台返回的格式不一样，Agent 需要统一提取：价格、户型、位置、联系方式
- 搜到的信息和知识库信息应该整合展示，而不是各说各的

**具体要做：**
- 给 Agent 加 system prompt 指令：从 Tavily 结果中提取结构化字段（价格、房型、面积、位置、联系方式）
- 搜索结果和知识库结果合并去重（同一个小区两处都有信息时合并）
- 考虑给 Tavily 搜索加更精准的 query 模板（如 `{community_name} rental room price 2026`）

---

## 3. HNSW 向量索引

**当前问题：** `rental_knowledge_base` 和 `units` 表的 `embedding` 列都没有创建向量索引，相似度搜索是全表顺序扫描（sequential scan）。

**为什么要优化：**
- 当前 132 条知识库数据和少量 units 数据，全表扫描没问题（毫秒级）
- 但如果 units 表数据增长到几百上千条（多房东录入房源），顺序扫描会明显变慢
- HNSW 索引可以把 O(n) 降到 O(log n)，数据量大时差距巨大
- pgvector 0.5+ 原生支持 HNSW，语法简单

**具体要做：**
```sql
CREATE INDEX ON rental_knowledge_base USING hnsw (embedding vector_cosine_ops);
CREATE INDEX ON units USING hnsw (embedding vector_cosine_ops);
```
- 等数据量超过 500 条时再加，当前不需要

---

## 4. 知识库持续扩充

**当前问题：** 知识库覆盖 42 所大学、132 个小区，但马来西亚有 20+ 所公立大学和几十所私立大学，覆盖面还有限。

**为什么要优化：**
- 用户来自不同大学，问到小众学校时知识库没有数据，Agent 只能靠联网搜索（信息质量不如知识库）
- 每个大学附近通常有 3-10 个可选小区，完整覆盖应该有 300-500 个小区
- 知识库数据是结构化的（评分、价格、设施），比网页搜索结果质量高得多

**具体要做：**
- 继续补充 JSON 数据：东马更多大学、二线城市大学（如 UMT、UMK、UniMAP）
- 导入流程已经打通：JSON 加数据 → 跑 `import_knowledge_base.py` → 自动入库 + 生成 embedding
- 考虑定期从外部平台抓取更新价格数据

---

## 5. Embedding 质量评估与调优

**当前问题：** 切换到 bge-m3 后没有做过检索质量测试，不确定相似度阈值 0.15 是否合理。

**为什么要优化：**
- 相似度阈值太高 → 搜不到相关小区（漏报）
- 相似度阈值太低 → 返回不相关的小区（噪声）
- bge-m3 对中英混合文本的检索效果需要实测验证
- 不同 query 类型（按大学搜、按价格搜、按设施搜）可能需要不同策略

**具体要做：**
- 准备 10-20 个测试 query，人工评估检索结果的准确性
- 调整 `match_threshold` 参数（当前 0.15，可试 0.2 / 0.25 / 0.3）
- 考虑是否需要对不同字段（小区名 vs 描述 vs 设施）分别加权

---

## 6. 知识库数据自动更新

**当前问题：** 知识库数据是静态的 JSON，导入后不会自动更新。价格、评分、设施等信息会随时间变化。

**为什么要优化：**
- 2026 年的价格到 2027 年可能过时
- 新楼盘建成、旧楼盘翻新等变化不会反映到知识库
- 用户看到过时信息会降低对 Agent 的信任度

**具体要做：**
- 建立定期更新机制（如每月跑一次外部数据抓取 + 重新导入）
- 给每条记录加 `last_verified` 字段，标记数据新鲜度
- Agent 回复时可以提示"以下价格为 2026 年数据，实际请以最新为准"

---

## 优先级排序

| 优先级 | 项目 | 原因 |
|--------|------|------|
| P0 | Render 环境变量更新 | 不改线上就用不了新功能 |
| P1 | 前端展示优化 | 用户体验直接影响可用性 |
| P1 | 外部搜索结果格式化 | 搜索结果质量直接影响回答质量 |
| P2 | 知识库扩充 | 覆盖更多大学 = 服务更多用户 |
| P2 | Embedding 质量评估 | 确保检索结果准确 |
| P3 | HNSW 向量索引 | 数据量小时不需要 |
| P3 | 数据自动更新 | 中长期维护问题 |
