# 前端与后端是怎么协作的？

## 一句话总结

前端 = 你看到的界面（按钮、输入框、页面），后端 = 存数据的地方（数据库）。前端通过 **发送网络请求** 告诉后端"我要做什么"，后端做完后把结果返回给前端，前端再更新界面。

---

## 先搞清楚：什么是前端？什么是后端？

### 前端（Frontend）
- 就是你在浏览器里 **看到和点击** 的一切
- 按钮、表格、图片、弹窗、侧边栏……
- 这个项目用的是 **Next.js**（React 框架）
- 代码在 `frontend/src/` 目录下

### 后端（Backend）
- 你 **看不到** 的东西，运行在服务器上
- 主要职责：存数据、取数据、处理业务逻辑
- 这个项目用的是 **Supabase**（一个在线数据库平台，底层是 PostgreSQL）
- 也可以理解为：后端 = 一台远程电脑上的数据库

---

## 核心问题：前端的按钮，怎么"连上"后端的数据库？

### 答案：Supabase 客户端（SDK）

在你的代码里，有一个关键文件：`frontend/src/lib/supabase.ts`

这个文件创建了一个 **Supabase 客户端对象**，它就像一个"遥控器"，前端通过它来远程操控数据库。

```typescript
// supabase.ts 里大概长这样
import { createClient } from '@supabase/supabase-js';

const supabase = createClient(
  'https://你的项目.supabase.co',  // 数据库地址
  '你的anon-key'                    // 访问密钥
);

export { supabase };
```

有了这个"遥控器"，前端代码就可以写：

```typescript
// 查数据
const { data } = await supabase.from('units').select('*');

// 删数据
await supabase.from('units').delete().eq('id', unitId);

// 改数据
await supabase.from('units').update({ status: 'rented' }).eq('id', unitId);
```

这些代码看起来像在"直接操作数据库"，但实际上每一条都会 **通过网络发请求** 给 Supabase 的服务器，由服务器去操作真正的数据库。

---

## 举个具体例子：点击"删除房源"按钮后发生了什么？

以管理员在 AdminPanel 中删除一套房源为例，完整走一遍：

### 第 1 步：用户点击按钮

在 `AdminPanel.tsx` 中，有一个删除按钮：

```tsx
<button onClick={() => deleteUnit(unit.id)}>
  删除此房源
</button>
```

用户看到的是一个普通的按钮，点击后触发 `deleteUnit` 函数。

### 第 2 步：前端代码执行 `deleteUnit` 函数

```typescript
const deleteUnit = async (unitId: string) => {
  // 1. 从数据库的 units 表中，删除 id 等于 unitId 的那一行
  const { error } = await supabase
    .from('units')
    .delete()
    .eq('id', unitId);

  if (error) {
    console.error('删除失败:', error);
    return;
  }

  // 2. 删除成功后，更新前端界面（从列表中移除这套房）
  setUnits(prev => prev.filter(u => u.id !== unitId));
};
```

### 第 3 步：Supabase 客户端发送网络请求

当代码执行到 `supabase.from('units').delete().eq('id', unitId)` 时，Supabase SDK 会在背后自动发一个 **HTTP 请求**（类似你在浏览器地址栏输入网址访问网页，但这次是程序自动发的）：

```
DELETE https://你的项目.supabase.co/rest/v1/units?id=eq.abc-123-uuid
Headers:
  apikey: 你的anon-key
  Authorization: Bearer 用户的登录token
```

这个请求的含义是："请删除 `units` 表中 `id` 等于 `abc-123-uuid` 的那一行记录"。

### 第 4 步：Supabase 服务器处理请求

Supabase 的服务器收到这个请求后：

1. **验证身份**：检查 `Authorization` 头里的 token，确认这个用户是谁
2. **检查权限（RLS）**：查看 `units` 表的 RLS（Row Level Security）策略，确认这个用户有没有权限删除这一行
   - 如果用户是管理员 → 允许删除
   - 如果用户是普通学生 → 拒绝删除，返回错误
3. **执行 SQL**：如果权限通过，执行 `DELETE FROM units WHERE id = 'abc-123-uuid';`
4. **返回结果**：删除成功后，返回一个成功的响应

### 第 5 步：前端收到响应，更新界面

`deleteUnit` 函数收到成功响应后，执行：

```typescript
setUnits(prev => prev.filter(u => u.id !== unitId));
```

这行代码把已经删除的那套房从 **前端的列表** 中也移除了。用户看到的是：点击删除 → 那套房从页面上消失了。

### 完整流程图

```
用户点击"删除房源"
       │
       ▼
前端代码执行 deleteUnit(id)
       │
       ▼
Supabase SDK 发送 HTTP 请求
   DELETE /rest/v1/units?id=eq.xxx
       │
       ▼
Supabase 服务器收到请求
       │
       ├── 验证用户身份（token）
       ├── 检查 RLS 权限（这个用户能删吗？）
       └── 执行 SQL: DELETE FROM units WHERE id = xxx
       │
       ▼
返回成功响应给前端
       │
       ▼
前端更新界面：从列表中移除这套房
       │
       ▼
用户看到：房源消失了 ✅
```

## 另一个例子：学生提交租房意向

学生在 PropertyListings 页面点击"我要租"按钮：

```
用户点击"我要租"
       │
       ▼
前端调用 submit_tenant_interest RPC
   supabase.rpc('submit_tenant_interest', { p_unit_id: id, p_note: '...' })
       │
       ▼
Supabase SDK 发送 HTTP 请求
   POST /rest/v1/rpc/submit_tenant_interest
       │
       ▼
Supabase 服务器执行数据库里的 RPC 函数
   → 检查用户身份
   → 往 tenant_interests 表插入一条记录
   → 返回成功
       │
       ▼
前端显示 Toast: "意向已提交 ✅"
```

注意这里调用的是 **RPC（远程过程调用）**，不是直接 `insert`。RPC 是数据库里预定义好的函数，封装了复杂的业务逻辑（比如检查是否重复提交、自动设置状态等）。

## 那 Python 后端（FastAPI）是干什么的？

这个项目有两个"后端"：

| | Supabase（数据库） | FastAPI（Python 服务器） |
|---|---|---|
| **做什么** | 存数据、取数据、用户登录 | AI 对话、智能推荐 |
| **在哪里** | Supabase 云平台 | Render 云服务器（或本地） |
| **前端怎么调用** | `supabase.from('xxx').select()` | `fetch('https://xxx/api/chat')` |
| **代码在哪** | `supabase/migrations/` | `backend/app/` |

当你在 AI 对话框里打字时：

```
用户输入: "帮我找 Monash 附近 1500 以内的房"
       │
       ▼
前端 AIChat.tsx 发送 HTTP 请求
   POST https://你的后端/api/chat
   Body: { message: "帮我找...", user_id: "xxx" }
       │
       ▼
FastAPI 服务器收到请求
   → agent.py 调用 DeepSeek 大模型
   → tools.py 执行工具（通勤计算、汇率查询等）
   → 流式返回回复
       │
       ▼
前端逐字显示 AI 的回复（打字机效果）
```

## 为什么有些操作不用 Python 后端？

因为 **Supabase 本身就够用了**。

Supabase 不只是一个数据库，它还提供：
- **认证系统**（登录/注册/Google OAuth）
- **存储服务**（图片/视频上传）
- **RLS 安全策略**（谁能读/谁能写，数据库层面控制）
- **RPC 函数**（在数据库里写复杂逻辑）

所以对于增删改查（CRUD）操作，前端直接通过 Supabase SDK 就能完成，不需要额外的 Python 服务器。

Python 后端只在需要 **AI 推理**（调用大语言模型）时才用到，因为 Supabase 数据库做不了 AI 对话。

## 两种模式：Mock 模式 vs Live 模式

你的项目还有一个巧妙的设计：**Mock 模式**（离线模拟）。

| | Mock 模式 | Live 模式 |
|---|---|---|
| **数据存在哪** | 浏览器的 `localStorage` | Supabase 云数据库 |
| **需要网络吗** | 不需要 | 需要 |
| **怎么判断** | 没有 `.env.local` 里的 Supabase 密钥时自动启用 | 有密钥时自动启用 |
| **用在哪** | 本地测试、无 Supabase 凭证时 | 线上生产环境 |

在 `supabase.ts` 中：

```typescript
const isRealSupabase = !!supabaseUrl && !!supabaseAnonKey;

if (isRealSupabase) {
  // 真实模式：用 Supabase SDK
  supabase = createClient(supabaseUrl, supabaseAnonKey);
} else {
  // Mock 模式：用 localStorage 模拟
  supabase = createMockClient();
}
```

前端代码完全不用改，`supabase.from('units').select()` 在两种模式下都能用：
- Live 模式：发网络请求给 Supabase
- Mock 模式：从 localStorage 读数据

这就是为什么你本地不需要 Supabase 凭证也能跑起来项目。

## 安全问题：前端直接操作数据库，不怕被乱删吗？

不会，因为有 **RLS（Row Level Security）** 保护。

RLS 是 PostgreSQL 数据库的安全策略，写在数据库层面，不是前端代码。即使有人打开浏览器控制台手动执行删除命令，数据库也会先检查权限：

```sql
-- 只有管理员才能删除房源
CREATE POLICY "Admins can delete units"
  ON units FOR DELETE
  USING (EXISTS (SELECT 1 FROM admin_users WHERE id = auth.uid()));
```

这意味着：不管你前端代码怎么写，数据库收到删除请求后，会先查 `admin_users` 表确认你是不是管理员。如果不是，直接拒绝。

前端代码只是"发起请求"，真正的安全控制在数据库的 RLS 策略里。

## 总结：一图流

```
┌─────────────────────────────────────────────────────────┐
│                    你的浏览器（前端）                      │
│                                                         │
│  AdminPanel.tsx  ──→  supabase.from('units').delete()   │
│  StudentPortal.tsx ──→ supabase.from('users').select()  │
│  AIChat.tsx  ──→  fetch('/api/chat')  ──→  FastAPI      │
│                                                         │
└───────────────────────┬─────────────────────────────────┘
                        │ HTTP 请求
                        ▼
┌─────────────────────────────────────────────────────────┐
│              Supabase 云平台（后端）                      │
│                                                         │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐  │
│  │   认证系统    │  │   PostgreSQL  │  │   存储服务    │  │
│  │  (Auth)      │  │   (数据库)    │  │  (Storage)   │  │
│  │              │  │              │  │              │  │
│  │ 登录/注册    │  │ units 表     │  │ 房源图片     │  │
│  │ Google OAuth │  │ users 表     │  │ 支付凭证     │  │
│  │ Magic Link   │  │ leases 表    │  │ 头像/证件    │  │
│  │              │  │ ...          │  │ ...          │  │
│  │              │  │ RLS 安全策略  │  │              │  │
│  └──────────────┘  └──────────────┘  └──────────────┘  │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

**前端** = 用户看到的界面 + 发请求的代码
**后端** = 收请求、验身份、查数据库、返回结果
**Supabase SDK** = 连接前端和后端的"遥控器"
**RLS** = 数据库的安全门卫，控制谁能做什么
